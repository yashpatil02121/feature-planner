# Contributing

Thanks for helping improve Feature Planner. This project is a Claude Code plugin made of Markdown skills, so most changes are edits to prompts, templates, and eval cases rather than code.

## Getting set up

You need [Claude Code](https://code.claude.com) and Node.js 22 or later.

```bash
git clone https://github.com/yashpatil02121/feature-planner.git
cd feature-planner
bash scripts/validate.sh
```

To try your working copy in another project:

```bash
claude --plugin-dir /path/to/feature-planner/plugins/feature-planner
```

Then run `/feature-planner:fp <feature>` in that session.

## Where things live

| Path | What it is |
| ---- | ---------- |
| `plugins/feature-planner/skills/fp/SKILL.md` | The planning workflow and its hard rules |
| `plugins/feature-planner/skills/fp/templates/` | The plan template |
| `plugins/feature-planner/evals/` | Eval cases and the shared fixture projects |
| `docs/` | Plan, architecture findings, configuration, testing |
| `examples/` | Plans generated by the current version |

## Making a change

1. **Open an issue first** for anything bigger than a fix, so we can agree on the behavior.
2. **Change the skill or template.** Keep `SKILL.md` under about 500 lines. Guidance lives in `SKILL.md` itself, so the planner doesn't spend extra reads loading it; only the templates are separate files.
3. **Add or update an eval case** when you change behavior. Each case is a `case.yaml` plus a `scaffold.sh` that builds a fixture from `evals/_fixtures/`. Prefer deterministic graders (`tool_used`, `file_exists`, `regex`) over `llm` graders, and anchor regexes on the plan's `Write` call (see `python-migration`).
4. **Run the checks:**

   ```bash
   bash scripts/validate.sh
   cd plugins/feature-planner
   claude plugin eval . --runs 1 --ablation none --scaffold --allow-tools Write Edit
   ```

   Evals use your Claude account or API key. A single pass costs about $1.60. See [docs/testing.md](docs/testing.md).
5. **Update `CHANGELOG.md`** under "Unreleased".
6. **Open a pull request.** Describe the behavior change and include the eval results.

## Guidelines

- **Planning stays read-only.** Never add `Edit`, `Bash`, or other mutating tools to the `fp` skill. The `read-only-guarantee` eval must keep passing.
- **Ground every claim.** Changes should make plans more tied to files the planner actually read, not less.
- **Keep plans proportional.** More template sections means longer plans for every user. Add structure only when it earns its place.
- **Use UTF-8 for all text files.** Watch for UTF-16 on Windows; CI rejects it.

## Releasing (maintainers)

1. Bump `version` in `plugins/feature-planner/.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`.
2. Update the `planner: feature-planner@<version>` header in `SKILL.md` and in the template. `validate.sh` checks that they match.
3. Move the "Unreleased" notes in `CHANGELOG.md` under the new version.
4. Run `bash scripts/validate.sh` and the eval suite.
5. Tag `v<version>` and create a GitHub release.
